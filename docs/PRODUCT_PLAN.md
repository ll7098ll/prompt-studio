# 프롬프트 스튜디오 공개 서비스 구축 계획

작성일: 2026년 10월 2일. 상태: 구현 전 설계안.

사용자가 UI 컴포넌트를 조립하고 레이아웃과 테마를 눈으로 확인한 뒤, 그 결정을 외부 AI에 전달해 실제 프론트엔드를 구현하는 공개 서비스를 만든다. 2026년 10월 2일 사용자의 후속 지시에 따라 **로그인 없이 즉시 사용하는 공개 서비스**로 확정했다. 계정·인증·클라우드 데이터베이스는 범위에서 제외하고 브라우저 저장·파일 백업·설계 스냅샷 링크 공유를 제공한다.

제품의 핵심 결과물은 재현 가능한 UI 설계다. 화면 구조, 디자인 값, 콘텐츠, 반응형 규칙, 인터랙션을 하나의 문서에 저장하고 미리보기와 AI 전달 자료가 그 문서를 함께 사용한다. 테마는 색상뿐 아니라 서체, 간격, 밀도, 모서리, 그림자, 상태 표현까지 포함한다.

아래의 기능 수량, 우선순위, 기술 선택은 제안이다. 기존 코드 평가는 초기 소스의 정적 검토에 기반한다. 현재 구현과 검증 결과는 `IMPLEMENTATION_STATUS.md`에서 별도로 관리한다.

후속 요구 반영: 컴포넌트 용어를 몰라도 고를 수 있도록 모든 항목에 작은 화면 예시·쉬운 이름·한 줄 설명·직접 조작하는 큰 미리보기를 제공한다. 추천 프리셋은 색만 바꾸는 변형 대신 브랜드, 스토어, 포트폴리오, 팀 작업 공간, 데이터, 학습, 도움말 등 용도별로 다르게 구성하고 모두 편집 가능한 노드로 연다. [Figma의 웹 디자인 트렌드](https://www.figma.com/ko-kr/resource-library/web-design-trends/)에서 선명한 컬러, 큰 타이포, 다크 모드, 네오브루탈리즘, 레트로와 콜라주를 참고한다. 유행하는 스타일은 선택 가능한 시작점으로 제공하며 기본 조작의 명확성·가독성·움직임 줄이기를 유지한다.

## 1 사용자와 성공 기준

첫 대상은 외부 코딩 AI로 웹 서비스를 만드는 개인 제작자와 소규모 팀이다. 디자인 전문 지식이 없어도 템플릿에서 출발할 수 있고, 필요한 사람은 개별 요소까지 편집할 수 있어야 한다.

대표 작업은 두 가지다. 하나는 SaaS 랜딩 페이지에 히어로, 기능 소개, 요금제, FAQ를 배치하는 작업이다. 다른 하나는 사이드바, 지표 카드, 표, 설정 화면이 있는 웹 앱을 구성하는 작업이다. 이 두 작업을 모두 지원해야 웹페이지와 애플리케이션의 공통 기반을 검증할 수 있다.

초기 검증 목표는 다음과 같다. 수치는 출시 후 측정하며 현재 성과로 간주하지 않는다.

- 처음 사용하는 사람이 템플릿 선택부터 첫 AI 전달 자료 생성까지 15분 이내에 완료한다.
- 동일한 프로젝트를 파일로 백업하거나 공유 링크로 전달해 다른 브라우저에서 열어도 내용과 테마가 유지된다. 브라우저 간 자동 동기화는 제공하지 않는다.
- 기본 테마 변경 한 번으로 같은 프로젝트의 모든 페이지가 일관되게 바뀐다.
- 페이지 순서, 컴포넌트 구조, 실제 색상 값과 반응형 규칙이 전달 자료에서 누락되지 않는다.
- 외부 AI가 만든 결과를 지정된 화면 폭과 상태에서 비교해 수정할 수 있다.

## 2 기존 코드에서 이어받을 것과 바꿀 것

| 영역 | 코드에서 확인한 상태 | 새 버전의 처리 |
| --- | --- | --- |
| 문서 모델 | `src/studio/types.ts`에 다중 페이지, 중첩 노드, 반응형, 생성 정책 타입이 있다 | 개념을 유지하고 실제 편집·저장·출력의 기준으로 완성한다 |
| 상태와 저장 | `use-studio-document.ts`에 실행 취소·다시 실행과 단일 localStorage 저장이 있다 | IndexedDB 기반 다중 프로젝트 저장, 저장 충돌 처리, 로컬 복구를 구현한다 |
| 조립 | `document.ts`가 노드를 블록 목록으로 평탄화하고 다시 루트 자식으로 교체한다 | 부모·자식 관계를 보존하는 트리 명령으로 교체한다 |
| 컴포넌트 | `component-presets.ts`의 웹 영역에 53개 정의가 있다 | 각 정의의 실제 렌더링·속성·동작을 점검해 재사용한다. 53개의 완성된 독립 컴포넌트로 계산하지 않는다 |
| 레이아웃 | 랜딩, 사이드바, 3단, 벤토 프리셋과 슬롯·열 너비가 있다 | 프리셋을 중첩 Flex/Grid 구조로 풀어 편집 가능하게 만든다 |
| 테마 | 비주얼 스타일·팔레트·서체·색상 조화 계산이 있다 | 유효한 데이터를 이관하고 실제 토큰 값과 사용자 수정값을 저장한다 |
| 커스텀 색상 | `ColorStudio.tsx`는 새 테마 객체를 생성하지만 `page.tsx`는 ID만 저장하고 정적 목록에서 다시 조회한다 | 커스텀 토큰을 문서에 보존한다. 현재 경로에서는 새 ID가 기본 테마로 대체되는 문제가 예상된다 |
| 프리뷰 | `CanvasRenderer.tsx`에 웹 외에 PPT·커머스·소셜 렌더링과 많은 분기가 섞여 있다 | 웹용 공통 렌더러와 컴포넌트 등록부로 분리한다 |
| 속성 | 현재 `ComponentPropValue`는 문자열·숫자·불리언·null이다 | 메뉴 항목, 표 열, 반복 카드 등을 위한 검증 가능한 객체·배열 속성을 지원한다 |
| AI 전달 | `prompt-engine.ts`에 구조 JSON과 생성 정책을 포함하는 기반이 있다 | 현재 평탄한 출력에 없는 부모 관계를 보존하고 전체 프로젝트 또는 선택 페이지를 명시해 출력한다 |
| 코드 출력 | `CodeExportModal.tsx`는 미리보기와 별개의 JSX/HTML 문자열 템플릿을 만든다 | 첫 버전은 정확한 설계 전달을 우선한다. 코드 출력 확장은 같은 구조와 컴포넌트 정의를 이용한다 |
| 검사 | `validation.ts`에 기본 구조·테마 존재 여부·주 텍스트 대비 검사가 있다 | 저장 형식 검사, 실제 화면 검사, 접근성 검사를 나눈다. 현 점수를 디자인 품질이나 접근성 인증으로 표시하지 않는다 |
| 서비스 기반 | 초기 `src/app`에는 프로젝트 관리·공유 라우트가 없다 | 프로젝트 관리, 브라우저 저장 충돌 처리, 공유 스냅샷과 정적 배포를 구현한다 |

기존 `layout_architecture_plan.md`의 다중 슬롯과 미리보기 구분은 이어받는다. 앞으로의 범위·우선순위 판단은 이 문서를 기준으로 한다. 기존 예제와 원본 프로젝트는 마이그레이션 검증 자료로 보존한다.

## 3 사용 흐름과 화면 구성

기본 흐름은 **템플릿 선택 → 컴포넌트 조립 → 테마 조정 → 반응형과 동작 확인 → 저장·공유 → AI 전달 자료 생성**이다. 단계가 강제되는 마법사 대신 언제든 조립과 테마 조정을 오갈 수 있는 편집기로 구성한다.

| 화면 | 사용자가 하는 일 |
| --- | --- |
| 서비스 소개와 예제 | 완성 예제를 열고 서비스의 결과물을 이해한다 |
| 프로젝트 목록 | 생성, 검색, 복제, 이름 변경, 삭제, 최근 작업 재개 |
| 템플릿 선택 | 랜딩·대시보드 등 출발점을 고르거나 빈 화면에서 시작 |
| 편집기 | 페이지·컴포넌트·레이아웃·콘텐츠·테마 편집 |
| 테마 실험실 | 동일한 샘플 UI에서 여러 디자인을 비교하고 저장 |
| 미리보기 | 편집 표시 없이 화면 크기와 인터랙션을 확인 |
| AI 전달 | 누락 검사, 전달 범위 선택, 프롬프트 복사, 파일 다운로드 |
| 공유 화면 | 게시된 버전을 열고 허용된 경우 내 프로젝트로 복제 |
| 저장 관리 | 브라우저 저장 안내, 프로젝트 삭제, 파일 백업과 복원 |

편집기 배치는 다음을 기본으로 한다.

- 상단: 프로젝트 이름, 저장 상태, 실행 취소, 화면 폭, 미리보기, 공유, AI 전달.
- 좌측: 페이지 목록, 레이어 트리, 검색 가능한 컴포넌트 라이브러리, 템플릿, 자산.
- 중앙: 선택한 페이지의 실제 렌더링. 선택 테두리와 삽입 위치는 편집 모드에서만 보인다.
- 우측: 선택한 요소의 콘텐츠·레이아웃·외형·동작·반응형 속성. 선택이 없으면 페이지 설정을 보여준다.
- 전체 테마 편집: 별도 패널에서 프로젝트 전체에 적용한다. 편집기 자체의 밝고 어두운 모드와 제작 중인 UI의 테마는 독립적이다.

기본 속성에는 제목·텍스트·색상·간격 등 자주 쓰는 설정을 배치한다. 고급 설정은 접어서 제공한다. 캔버스에서 요소를 선택하면 레이어와 속성 패널도 같은 대상을 가리켜야 한다. 부모 선택, 키보드 이동, 검색 삽입을 제공해 드래그에만 의존하지 않게 한다.

공개 베타에서는 데스크톱에서 편집하고 모바일에서 공유 미리보기를 보는 경험을 우선한다. 모바일 전체 편집기는 후속 범위다.

## 4 UI 라이브러리의 범위와 등록 기준

라이브러리를 네 층으로 구성한다. 사용자는 큰 블록으로 빠르게 시작하고 필요할 때 내부 요소를 편집한다.

| 층 | 구성 예 |
| --- | --- |
| 기본 요소 | Button, Input, Select, Checkbox, Switch, Badge, Avatar, Text, Image, Divider |
| 조합 패턴 | 검색창, 폼 필드, 카드, 탭, 아코디언, 모달, 드롭다운, 페이지네이션, 표 |
| 화면 구역 | 헤더, 사이드바, 히어로, 기능 소개, 요금제, 지표 영역, 로그인 폼, 설정 패널, 푸터 |
| 페이지 템플릿 | SaaS 랜딩, 대시보드, 목록, 상세, 설정, 로그인, 포트폴리오, 상품 소개 |

장기 카탈로그는 입력, 탐색, 데이터 표시, 피드백, 오버레이, 콘텐츠, 미디어, 레이아웃, 상거래의 범주로 관리한다. 달력·날짜 선택, 고급 차트, 칸반, 트리, 커맨드 메뉴, 파일 업로드, 타임라인, 캐러셀 등도 이 체계로 확장한다.

공개 베타의 제안 목표는 기본 요소 약 25종, 조합 패턴 약 15종, 화면 구역 약 15종, 템플릿 6종이다. 크기·색상·배치 변형을 별도 컴포넌트 수로 세지 않는다. 수량은 아래의 완성 기준을 충족하는 속도에 따라 조정한다.

등록되는 각 컴포넌트는 다음을 함께 가진다.

- 고유 ID와 버전, 분류, 검색어, 기본 콘텐츠, 사용 예.
- 허용 속성과 값의 범위, 편집 패널 정의, 자식 요소를 넣을 수 있는 슬롯.
- React 렌더러와 디자인 토큰 연결, 크기·강조·배치 변형.
- 해당하는 상태: 기본, hover, focus, disabled, loading, error, empty, selected, open.
- 모바일 배치 규칙과 키보드 동작. 모든 상태를 모든 요소에 억지로 적용하지 않는다.
- AI에 전달할 목적·구조·동작 명세와 알려진 제약.
- 긴 한국어·긴 영문·빈 콘텐츠·이미지 실패·큰 텍스트로 확인한 예제.

등록부 하나에서 라이브러리 카드, 속성 편집기, 프리뷰, 전달 명세를 연결한다. 렌더러에서 컴포넌트 이름의 일부를 검사해 모양을 추측하는 분기는 제거한다. 사용자가 만든 블록 저장과 재사용 가능한 공통 컴포넌트는 후속 단계로 확장한다.

## 5 레이아웃 편집과 반응형 미리보기

기본 구조는 Page 아래에 Section, Container, Stack, Grid, Component가 중첩되는 형태다. 텍스트와 이미지는 편집 가능한 기본 컴포넌트다. 자유 배치는 부모 컨테이너 안에서 이루어지며 실제 웹의 Flex와 Grid 규칙에 맞춰 조작한다.

첫 버전에서 제공할 편집 동작은 추가, 이동, 복제, 삭제, 그룹화, 그룹 해제, 숨김, 편집 잠금, 정렬, 너비 조절이다. 드래그는 삽입 위치와 유효한 부모를 표시하고 잘못된 중첩·자기 자식 안으로 이동을 차단한다. 이동 버튼과 키보드 조작도 동일한 편집 명령을 사용한다.

레이아웃 속성은 방향, 줄바꿈, 정렬, 간격, 안팎 여백, 최대 너비, 고정·자동·채우기 너비, 열 수와 열 점유, 화면별 표시 여부를 포함한다. 절대 위치로 모든 것을 배치하는 무한 캔버스는 후속 실험 범위로 둔다.

반응형은 기본값을 작은 화면부터 적용하고 지정된 breakpoint 이상에서 변경값을 합성한다. 예를 들어 카드 영역은 모바일 1열, 태블릿 2열, 데스크톱 3열로 설정한다. 상속값·직접 수정값을 구분하고 해당 화면의 수정만 초기화할 수 있어야 한다.

미리보기의 기본 폭은 390, 768, 1440 CSS px로 제안하고 사용자 지정 폭을 허용한다. 화면 폭과 확대 배율은 독립적이다. 1440px 화면을 50%로 축소해 봐도 레이아웃 판정은 1440px이어야 한다.

캔버스는 별도 문서 안에서 렌더링하도록 iframe을 우선 검토한다. iframe이 독립된 browsing context를 제공한다는 점을 이용해 편집기 CSS와 화면 폭의 영향을 분리하려는 설계 선택이다. 실제 모바일 기기의 브라우저·터치 환경까지 재현한다는 의미는 아니다. [MDN iframe 문서](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

프리뷰와 캡처는 같은 렌더러를 사용한다. 글꼴·이미지 로딩 완료를 확인한 뒤 캡처하고 선택 테두리, 조작 버튼, 장식용 기기 프레임은 결과 이미지에서 제외한다. 두 테마 비교는 같은 콘텐츠와 같은 폭을 사용하며, 다수의 무거운 라이브 프레임을 동시에 열지 않는다.

## 6 테마와 디자인 토큰

테마를 다음의 독립된 축으로 편집한다. 예를 들어 구조는 미니멀, 색상은 따뜻한 베이지, 글꼴은 명조, 밀도는 넉넉하게 선택할 수 있다.

| 축 | 설정 내용 |
| --- | --- |
| 비주얼 스타일 | 미니멀, 기업형, 에디토리얼, 소프트, 브루탈리즘, 글래스 등 |
| 색상 | 브랜드, 배경, 표면, 텍스트, 경계, 상태 색상과 라이트·다크 대응 |
| 타이포그래피 | 제목·본문·숫자 서체, 크기 단계, 굵기, 줄 높이, 자간 |
| 간격과 밀도 | 간격 단계, 컨테이너 폭, 요소 높이, 섹션 여백 |
| 형태 | 모서리, 선 두께, 그림자, 표면 효과 |
| 움직임 | 시간, easing, 상태 전환, 움직임 줄이기 대응 |

토큰은 원시 값 → 용도별 값 → 컴포넌트 값으로 나눈다. 예를 들어 `blue.600` → `action.primary.background` → `button.primary.background`다. 사용자는 의미 있는 역할을 수정하고, 시스템은 영향을 받는 요소를 보여준다.

색상만으로 모든 스타일을 표현하지 않는다. 서체, 밀도, 테두리와 표면 표현의 조합을 스타일 레시피로 저장한다. 기본 테마 약 8종과 팔레트 약 12종을 제안하되 완성도 기준을 통과한 것부터 공개한다.

프로젝트에는 프리셋 ID·버전과 함께 실제 토큰 스냅샷, 사용자 수정값, 라이트·다크 대응을 저장한다. 라이브러리의 프리셋이 바뀌어도 기존 프로젝트가 자동으로 변형되지 않는다. 외부 도구와 교환하는 토큰 파일은 DTCG의 게시된 2025.10 형식에 맞추는 방향을 권장한다. 이는 디자인 토큰 교환 형식이며 전체 페이지 구조까지 정의하지는 않는다. [DTCG 게시 형식](https://www.designtokens.org/tr/2025.10/format/).

테마 변경 시 전체 프로젝트를 갱신하고 요소별 명시적 수정은 유지한다. 일괄 초기화는 별도 동작으로 제공한다. 새로고침, 복제, 가져오기, 실행 취소 후에도 커스텀 토큰이 보존되어야 한다. 테마 저장과 비교 기능에는 이름, 미리보기, 버전을 포함한다.

검사는 텍스트와 배경뿐 아니라 버튼의 글자·배경, 경계, 포커스 표시 등 적용되는 조합을 다룬다. 그래디언트·사진 위 텍스트처럼 자동 판정이 제한되는 경우 별도 확인 대상으로 표시한다. 스타일 이름만으로 접근성이 보장된다고 표시하지 않는다.

## 7 콘텐츠와 인터랙션

헤드라인 한 개로 전체 화면의 내용을 추정하는 대신 요소별 텍스트, 메뉴 항목, 링크, 이미지, 표 열·행, 차트 샘플 데이터를 편집한다. 자산에는 파일 ID, 대체 텍스트, 크기, 비율, 사용 출처를 기록한다. 프리뷰의 샘플 데이터와 실제 서비스 데이터 연결 요구사항을 구분한다.

인터랙션은 선언적인 동작으로 저장한다. 초기 범위는 페이지 이동, 특정 구역으로 스크롤, 탭 전환, 아코디언 열기, 모달 열고 닫기, 입력 검증과 제출 결과 데모다. 편집 모드에서는 선택이 우선하고 미리보기 모드에서는 해당 동작을 실행한다.

실제 결제·인증·이메일 전송·서버 데이터 수정은 프리뷰에서 실행하지 않는다. 예를 들어 로그인 화면은 성공·오류 상태를 미리 보여주고, 실제 인증 연동은 AI 구현 요구사항으로 전달한다. 재현할 수 없는 동작은 완성된 것처럼 표현하지 않고 미정 요구사항으로 남긴다.

초기 프로젝트 JSON과 컴포넌트 속성에는 사용자가 입력한 임의 JavaScript를 허용하지 않는다. 접근성 동작 설계에는 해당 위젯의 키보드·포커스 관례를 함께 적용한다. [WAI ARIA 패턴 안내](https://www.w3.org/WAI/ARIA/apg/patterns/).

## 8 AI 전달 자료와 재현성 검증

기본 내보내기는 두 가지다. 빠른 전달은 자체적으로 필요한 값이 들어 있는 프롬프트를 복사한다. 정밀 전달은 프롬프트·구조·토큰·이미지를 묶은 파일 패키지를 제공한다. 파일을 받을 수 없는 AI에는 한 페이지씩 나눈 텍스트 출력을 제공한다.

| 파일 | 담는 내용 |
| --- | --- |
| `START_HERE.md` | 프로젝트 목적, 파일 읽는 순서, 대상 기술, 구현 순서, 미정 사항 |
| `PROMPT.md` | 사람이 읽을 수 있는 실행 지시와 고정·허용 변경 조건 |
| `ui-spec.json` | 페이지·부모 관계·순서·속성·레이아웃·반응형·콘텐츠·동작 |
| `theme.tokens.json` | 원시·용도별·컴포넌트 토큰과 모드별 값 |
| `theme.css` | 실제 렌더링에 사용한 CSS 변수와 기본 타이포그래피 규칙 |
| `component-specs.json` | 사용된 컴포넌트의 구조, 버전, 변형, 상태와 동작 설명 |
| `assets/`와 자산 목록 | 필요한 이미지와 글꼴 정보, 경로, 사용 조건, 대체 자산 지침 |
| `screenshots/` | 선택한 페이지의 화면 폭·테마·상태별 기준 이미지 |
| `ACCEPTANCE.md` | 구현 결과에서 확인할 구조·화면·동작 체크 항목 |
| `manifest.json` | 문서 버전, 프로젝트 revision, 렌더러·등록부 버전, 생성 조건, 파일 해시 |

계정 ID, 공유 비밀 토큰, 서명 URL, 비공개 편집 메모는 전달 자료에서 제외한다. 자산은 패키지 안에서 해석되는 경로 또는 명시적인 대체 지침을 사용한다. 일시적인 서명 URL만 내보내 자료가 나중에 깨지는 일을 방지한다.

전달 규칙은 구체적인 값으로 작성한다. 예를 들어 “카드 높이는 자동, 간격은 24px, 768px 미만은 1열, 1280px 이상은 3열”처럼 명시한다. “세련되게”, “적당한 간격” 등의 표현은 보조적인 의도 설명에만 사용한다.

사용자가 고정할 수 있는 것은 페이지 구조, 테마, 콘텐츠, 동작이며 AI에게 허용할 것은 코드 구성, 내부 함수 분리, 미정 콘텐츠 보완 등이다. 편집 잠금과 AI 변경 금지는 다른 개념으로 저장한다. 기본 우선순위는 구조·토큰·동작 명세를 먼저 따르고 이미지는 시각적 참고로 쓰는 것이다. 자료끼리 모순이 발견되면 내보내기 전에 수정하도록 안내한다.

첫 출력 대상은 React·TypeScript·Tailwind 기반으로 좁힌다. Next.js 통합 지침을 제공하되 기존 프로젝트에 적용할 때는 해당 프로젝트의 버전·설정을 먼저 읽게 한다. 특정 AI 제품명에 설계 데이터를 종속시키지 않고 대상별 지시문만 교체한다.

문장과 이미지만으로 임의의 외부 AI가 동일한 결과를 낸다고 보장할 수는 없다. 따라서 대표 랜딩·대시보드·설정 화면을 외부 코딩 AI 2종 이상에 전달하는 평가를 별도 진행한다. 사용한 모델·날짜·입력·결과를 기록하고 다음 항목을 비교한다.

- 페이지와 컴포넌트의 누락, 부모 관계, 배치 순서.
- 토큰 값, 글꼴, 간격, 그리드, 반응형 전환.
- 로딩·오류·빈 상태, 탭·모달·폼의 지정 동작.
- 같은 폭과 같은 자산으로 캡처한 이미지의 차이와 사람의 검토.
- 사람이 결과물을 고치는 시간과 수정 횟수.

후속 버전은 이전 전달 revision과 현재 revision의 차이만 설명하는 수정 프롬프트를 만든다. 외부 코드 자동 가져오기와 양방향 동기화는 별도 기능으로 취급한다.

## 9 문서와 렌더링 아키텍처

처리 흐름은 **문서 → 형식 검증·버전 변환 → 값 해석 → 공통 렌더링 계획 → 프리뷰·캡처·전달 명세**로 통일한다. 프롬프트 엔진이 임의로 레이아웃을 다시 추정하지 않게 한다.

문서의 핵심 필드는 다음과 같다. 저장 충돌 판정용 버전과 문서 형식의 schemaVersion은 구분한다.

| 모델 | 주요 필드 |
| --- | --- |
| ProjectDocument | schemaVersion, pages, nodes, theme, assets, interactions, generationPolicy |
| Page | id, name, slug, rootNodeId, metadata |
| Node | id, kind, componentRef, childIds, props, layout, responsive, styleOverrides, editorLocked |
| ComponentRef | id, version, variant |
| Theme | presetRef, sourceTokens, overrides, modes, typography, breakpoints |
| Interaction | trigger, action, target, state, validationRules |
| GenerationPolicy | targetStack, scope, lockedPaths, allowedChanges, unresolvedRequirements |

노드 참조는 ID 기반으로 정규화해 이동·복제·검색을 처리한다. 각 페이지의 루트부터 트리로 순회하며 순환, 중복 부모, 누락된 자식, 중복 ID를 검사한다. props는 컴포넌트별 스키마로 검증하고 배열 길이·트리 깊이·전체 크기에 제한을 둔다.

편집 명령은 add, move, updateProps, updateLayout, setTheme, delete, duplicate 등으로 모은다. 한 번의 드래그 또는 연속 입력을 하나의 실행 취소 단위로 묶는다. 선택 상태·패널 열림·확대 배율 같은 작업 UI 상태는 설계 데이터에서 분리한다.

임의 입력으로 CSS 클래스 문자열을 조립하기보다 허용된 값의 매핑과 CSS 변수를 이용한다. 미리보기, 저장, 전달 시 유효한 같은 값을 사용한다. 컴포넌트 기본값을 적용한 최종 값도 내보내 해석 차이를 줄인다.

사용자 파일의 미지의 컴포넌트는 안내용 자리와 원본 데이터로 보존한다. 지원하지 않는 속성이나 버전을 조용히 삭제하지 않는다. v1 가져오기는 원본 백업을 만든 뒤 새 문서로 변환하고, 기존 ID만 남아 실제 값이 없는 커스텀 테마는 복구 불가 항목으로 사용자에게 알린다.

## 10 로그인 없는 프로젝트 저장

템플릿 선택 즉시 편집할 수 있다. 프로젝트 생성·복제·삭제, 자동 저장, 실행 취소, 파일 백업·복원과 수동 체크포인트를 제공한다. 브라우저의 IndexedDB에 프로젝트를 저장하고 localStorage에는 저장 전 복구 자료를 보관한다. 두 저장소의 역할과 실패 상태를 구분한다.

짧은 연속 입력을 묶어 저장하며 저장소 트랜잭션이 완료된 뒤에만 저장 완료로 표시한다. 브라우저 저장 공간 부족 또는 저장 기능 차단 시 재시도와 파일 다운로드를 제공한다. 브라우저 데이터 삭제 시 프로젝트가 지워질 수 있음을 프로젝트 목록에서 안내한다.

각 기록에는 문서와 별도의 저장 버전이 있다. 쓰기 트랜잭션에서 읽은 버전이 편집을 시작한 버전과 다르면 저장을 중지하고 충돌을 알린다. 두 탭의 편집을 조용히 덮어쓰지 않는다. 복구 자료가 남아 있으면 원본을 보존하면서 사본으로 열 수 있게 한다.

현재 설치된 Next.js·React·TypeScript·Tailwind를 유지한다. 로그인과 데이터 서버 없이 정적 배포할 수 있도록 설계하고 설치된 `node_modules/next/dist/docs/`의 해당 버전 안내를 따른다. 사용자 프로젝트는 서비스 서버에 업로드하지 않는다.

## 11 공유와 공개 서비스 운영

프로젝트는 기본적으로 사용자의 브라우저에만 있다. 공유 시 설계 문서를 압축해 URL fragment에 포함한다. 링크를 가진 사람은 그 시점의 화면을 미리보고 JSON을 내려받거나 자신의 브라우저에 사본을 저장한다. 원본을 수정해도 발행한 링크의 내용은 바뀌지 않는다.

서버에 공유 기록을 두지 않으므로 링크 회수·만료·개인별 권한은 제공하지 않는다. 공유 화면에서 이를 명확히 안내한다. 크기 제한을 넘는 프로젝트는 JSON 파일로 전달한다. fragment는 페이지 요청 경로에 포함되지 않지만 링크를 받은 사람에게는 모든 설계 데이터가 보인다.

출시 전에 다음 운영 작업을 포함한다.

- 저장 실패, 내보내기 실패, 파일 누락을 알려주는 사용자 오류 화면.
- 프로젝트 파일 크기·노드 수·중첩 깊이와 공유 링크 압축 해제 크기 제한.
- 파일 스키마 검사, 안전한 외부 URL 처리, 프로젝트 삭제, 데이터 백업과 복원 연습.
- 개인 설계 내용을 원격 분석·오류 수집 서비스로 전송하지 않는 기본 설정.
- 브라우저 캡처 작업의 시간·이미지 크기 제한과 실패 복구.
- 배포 빌드 검증, 정적 자산 캐시, 알려진 배포 버전의 롤백 절차.

첫 버전은 등록된 컴포넌트만 실행한다. iframe은 레이아웃 격리 수단이며 그 자체로 임의 코드를 안전하게 실행해 주는 보장은 아니다. 외부 코드 실행이 필요해지는 시점에 별도 출처와 실행 환경을 설계한다.

## 13 구현 순서와 단계별 완료 조건

전체를 한 번에 교체하지 않고 기능별로 검증해 새 편집기로 이관한다. 기존 데모는 새 경로의 핵심 시나리오가 검증될 때까지 비교 자료로 유지한다. 문서 변환은 원본을 덮어쓰지 않는다.

| 단계 | 구현 묶음 | 완료 조건 |
| --- | --- | --- |
| 0 설계 재현 검증 | 새 문서 스키마, 등록부, 토큰, 공통 렌더러, 최소 전달 자료 | 작은 랜딩과 대시보드 샘플이 같은 문서로 렌더링·직렬화된다. 커스텀 색상과 중첩 관계가 왕복 보존된다 |
| 1 서비스 기반 | 프로젝트 목록, IndexedDB 저장, 파일 백업, 충돌 처리 | 새로고침 복원, 두 탭 저장 충돌, 파일 복원, 로컬 실패 복구를 확인한다 |
| 2 조립 편집기 | 페이지·레이어·캔버스·속성 패널, 중첩 이동, 실행 취소, 반응형 | 랜딩·대시보드·설정의 세 화면을 코드 수정 없이 만들고 크기별로 확인한다 |
| 3 테마와 카탈로그 | 의미별 토큰, 모드, 속성·상태·동작, 템플릿 확장 | 같은 프로젝트의 테마 교체와 컴포넌트 상태 변경이 프리뷰·저장·전달에 모두 반영된다 |
| 4 AI 전달 완성 | 다중 페이지 출력, 자산, 캡처, 검증, 다운로드, 실패 복구 | 외부 AI 구현 평가를 수행하고 반복되는 구조·토큰 누락을 수정한다 |
| 5 공유와 베타 | 스냅샷 뷰어, 링크·파일 크기 제한, 오류 처리, 사용성 개선, 공개 배포 | 별도 브라우저에서 공유 열기와 복제가 가능하고 신규 사용자가 생성→조립→저장→공유→AI 전달을 도움 없이 완료한다 |
| 6 확장 | 사용자가 자주 막히는 컴포넌트, 공통 요소, 팀 기능, 수정 프롬프트 | 실제 사용 데이터로 우선순위를 결정한다 |

기간은 인력과 주당 투입 시간이 정해진 뒤 산정한다. 단계 0에서 드래그·iframe 통신·외부 AI 재현의 난이도를 확인하고 나머지 작업을 다시 추정한다. 달력보다 각 단계의 완료 조건을 출시 판단 기준으로 사용한다.

## 14 검증과 출시 판단

문서·토큰·편집 명령에는 변환과 왕복 보존을 검증하는 테스트를 둔다. 특히 중첩 이동·복제 ID·실행 취소·버전 변환·잘못된 import를 검증한다. 저장 버전 충돌은 두 브라우저 탭의 실제 IndexedDB 트랜잭션으로 확인한다.

브라우저 검증은 프로젝트 생성부터 내보내기까지의 핵심 흐름, 키보드 조작, 원본 저장소가 없는 브라우저에서 공유 열기, 저장 실패 복구를 대상으로 한다. 컴포넌트별 이미지를 무조건 모든 조합으로 늘리지 않고 대표 상태와 테마를 고정한 시각 회귀 검사와 필수 전체 템플릿 검사를 조합한다.

출시 전 필수 확인 항목은 다음과 같다.

1. 한국어 입력 도중 글자가 끊기거나 실행 취소가 조합 입력을 훼손하지 않는다.
2. 커스텀 색상·폰트·간격과 중첩 구조가 저장·복제·가져오기 후 유지된다.
3. 390·768·1440px 및 전환점 전후에서 가로 넘침, 잘림, 잘못된 순서가 없다.
4. 긴 텍스트, 빈 목록, 로딩, 오류, 이미지 실패가 레이아웃을 무너뜨리지 않는다.
5. 키보드로 주요 조작을 완료하고 모달·메뉴의 포커스가 예측 가능하게 이동한다.
6. 전달 파일과 캡처가 같은 프로젝트 revision·테마·화면 폭을 가리킨다.
7. 미저장 편집을 보존하고 충돌을 알리며 공유 자료의 검증과 크기 제한을 지킨다.
8. 외부 AI 결과의 누락과 차이를 확인하고 사용자에게 수정 가능한 자료를 제공한다.

성능은 기준 브라우저·기기·데이터를 정해 측정한다. 초기 목표는 한 페이지 200개 노드와 50행 샘플 표에서 일반 속성 변경 반영 p95 100ms 이내다. 이는 설계 목표이며 현재 측정 결과가 아니다. 무거운 자산 로드, 전체 테마 변경, 캡처는 별도로 측정한다.

사용 지표는 첫 전달 자료 생성률, 첫 완료까지의 시간, 저장 실패율, 복구 성공률, 공유 이용률, 재방문, 외부 AI 결과 수정 시간을 본다. 컴포넌트 수와 클릭 수만으로 제품 성공을 판단하지 않는다.

## 15 첫 구현 묶음과 남은 결정

첫 구현 묶음은 단계 0이다. Page·Stack·Grid와 Button·Text·Image·Card·Input을 연결하고, 헤더·히어로·사이드바·지표·간단한 표 샘플을 올린다. 동일한 문서에서 두 화면 폭, 두 테마, JSON 저장, 프롬프트와 토큰 출력을 확인한다. 이후 단계 1에서 다중 프로젝트 저장과 복구를 연결한다.

| 결정 | 현재 기준 |
| --- | --- |
| 서비스 형태 | 로그인 없는 공개 서비스. 사용자가 후속 지시로 확정 |
| 첫 사용자 | 개인 제작자와 소규모 팀을 위한 개인 작업 공간. 제안 |
| 핵심 대상 화면 | 랜딩과 SaaS 웹 앱. 제안 |
| AI 역할 | 외부 AI가 실제 프론트엔드를 구현. 사용자의 원래 흐름을 따른다 |
| 첫 출력 기술 | React·TypeScript·Tailwind, Next.js 연동 지침. 제안 |
| 저장 기술 | IndexedDB 자동 저장, localStorage 복구, JSON 백업, 압축된 URL 스냅샷 공유 |
| 편집 언어 | 한국어 우선, 영문 UI 콘텐츠와 출력 지원. 제안 |
| 브랜드·도메인·과금 | 미정. 핵심 편집기 설계를 막지 않는다 |
| 인력·일정·운영 예산 | 미정. 단계 0 검증과 함께 구체화 |

완료된 디자인의 구조와 값을 안정적으로 보존하고 전달하는 것이 첫 출시의 기준이다. 이 기반이 갖춰지면 컴포넌트·테마·AI 연결 대상을 늘릴 때 기존 사용자의 프로젝트를 유지하면서 확장할 수 있다.
